# 실제 브라우저 플레이 검증 — 2026-09-09

> 이 문서는 당시(mock 모드) 기록이다. 독립 사용자 멀티플레이는 이후 구현되어 지금은 운영 주소에서 정상 동작한다. 배포된 주소로 다인 E2E를 돌리는 방법과 최신 결과는 `docs/DEPLOYMENT.ko.md`와 [HANDOFF-20260921.ko.md](../claudedocs/HANDOFF-20260921.ko.md)를 본다.

## 판정

**실제 독립 사용자 멀티플레이는 아직 불가능하다.** 로컬 데모의 카드 게임 흐름은 통과했다. 이 둘을 같은 성공 판정으로 묶지 않는다.

## 도구와 조건

- Aside CLI/REPL로 사용자 브라우저의 실제 화면을 직접 조작했다. 실제 닉네임 `Aside 검수`를 만들고 3인 방에 데모 대원 루나·코멧을 추가했다.
- Playwright Chromium: PC 및 Pixel 7 모바일 에뮬레이션. 실제 물리 스마트폰 검증은 아니다.
- 독립 사용자는 각각 다른 BrowserContext로 만들었다. 쿠키/localStorage를 공유하거나 복사하지 않았다.
- 실제 Supabase는 연결하지 않았다. 기본 mock 모드, localhost:5173의 실행 중인 앱을 사용했다.

## 독립 사용자 3명 입장 시도

각 PC/모바일 프로젝트에서 A가 방을 만들고 UI의 초대 링크를 복사했다. B/C는 각각 독립된 브라우저 저장소로 해당 링크를 열고 닉네임을 입력했다.

| 확인 | 결과 |
| --- | --- |
| A 방 생성 | 정상 |
| 독립 B 초대 입장 | 실패: “초대 링크를 찾을 수 없습니다. 로컬 데모 링크는 같은 브라우저에서만 열립니다.” |
| 독립 C 초대 입장 | 동일하게 실패 |
| 같은 브라우저 프로필의 새 탭 | 새 닉네임을 입력해도 기존 A 좌석으로 복귀 |
| A의 다른 탭에서 준비 변경 | 원래 탭에 정상 동기화 |
| 1/3명 상태에서 시작 | 비활성화 정상 |

재현 테스트 `tests/e2e/multiplayer-boundary.spec.ts`는 이 **미구현 상태**를 명시적으로 확인한다. 2개 테스트 통과라는 뜻은 차단 현상을 재현했다는 뜻이며, 다인 플레이를 통과했다는 뜻이 아니다.

원인: MockService는 전체 방을 해당 브라우저의 localStorage에만 보관하고, identity도 같은 저장소에서 하나만 사용한다. BroadcastChannel/storage 이벤트는 동일 origin·저장소 영역 안에서만 동기화된다. SupabaseService 어댑터는 준비되어 있지만 Edge의 PendingRepository는 실제 게임 저장소가 없고 501을 반환한다.

## Aside 직접 플레이

UI 버튼으로 다음 흐름을 직접 확인했다. 내부 손패 주입, 서버 응답 가로채기, 상태 강제 변경은 하지 않았다.

1. 방 생성 → 3명 채우기 → 전원 준비 → 미션 1 시작.
2. 14/13/13장 배분, 코멧이 로켓 4 사령관, 목표 파랑 3 담당자 코멧 확인.
3. 본인의 파랑 7을 “이 색은 이 카드뿐”으로 교신. 손패에는 카드가 유지됨.
4. 코멧이 로켓 3으로 선도. 본인 손에 로켓 1이 있으므로 파랑 7 선택 시 제출 불가, 로켓 1 선택 시 제출 가능 확인.
5. 본인 로켓 1 제출, 루나가 파랑 3 제출. 코멧의 로켓 3이 트릭을 획득하고 담당 목표를 완료해 **미션 성공**.
6. 새로고침 후 성공 결과·손패 13장·교신 유지 확인.
7. 다음 임무 버튼으로 **미션 2 브리핑** 진입, 카드 재분배 및 교신 초기화 확인.

이 과정의 다른 대원 두 명은 실제 원격 사용자가 아닌 데모 대원이다.

## Playwright 게임 흐름

| 범위 | 케이스 수 | 확인 결과 |
| --- | ---: | --- |
| 3·4·5인 × 미션 1~4 × PC/모바일 | 24 | 교신, 차례, 카드 플레이, 정상 실패 판정, 결과 복귀, 동일 미션 재도전 모두 통과 |
| 3·4·5인 미션 1 성공 × PC/모바일 | 6 | 성공 판정, 새로고침 유지, 다음 미션 2 진입 모두 통과 |
| 독립 사용자 입장 제한 × PC/모바일 | 2 | 위 제한 현상 재현 |

게임 데모 30개 + 제한 확인 2개, 총 32개 검증이다. 데모는 협력 전략이 없는 대원이므로 실패 결과 자체는 오류가 아니다. 24개 기본 흐름의 결과는 실패이며 별도 6개 성공 흐름으로 성공/다음 임무 분기도 확인했다.

재현 가능한 분배를 위해 테스트에서만 Math.random을 seed로 고정했다. 성공 흐름은 React 등의 난수 사용에 영향을 받지 않도록 임무 시작 직전에 seed를 초기화했다. 카드/목표/승자를 직접 주입하지 않고 모두 UI로 진행했다. 실제 서비스의 난수는 변경하지 않았다.

## 발견 후 수정

Aside에서 다른 대원의 브리핑 확인을 진행해도 대원 목록은 카드 장수만 표시하여 버튼이 반응하지 않은 것처럼 보였다. `src/App.tsx`에서 브리핑 단계의 각 대원에게 **브리핑 확인 중 / 브리핑 확인 완료**를 표시하도록 수정했다. 성공 경로 6개에서 수정한 표시와 단계 진행을 함께 확인했다. 프로덕션 빌드·타입 검사 통과, graphify 코드 그래프 갱신 완료.
