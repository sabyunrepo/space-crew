## 4. 반드시 알아야 할 함정

| 함정 | 내용 |
|---|---|
| 하위 경로 금지 | 플랫폼 라우터는 `/functions/v1/<이름>`만 받는다. API 경로는 `?route=`로 보낸다 |
| jsonb 이중 인코딩 | postgres.js는 jsonb로 타입이 정해진 파라미터를 또 `JSON.stringify` 한다. 항상 `$n::text::jsonb`. 회귀 테스트가 고정하고 있다 |
| SQL 제한 | `sbp db sql`은 한 문장만, `$`·`--`·중간 `;` 금지. 스키마·함수 생성 불가 → 표는 `public.crew_*` |
| 함수 env | 워커는 allowlist env + `APP_*` 시크릿만 받는다. 프로젝트 UUID는 빌드 시 주입 |
| 로그 없음 | 함수 로그가 없다. 500 응답의 `error.detail`(SQLSTATE + 메시지)이 유일한 단서다 |
| 방송 누락 | private Broadcast는 가끔 누락된다. 클라이언트가 4초마다 재조회하고 캐시는 3초까지만 쓴다(`src/services/supabase.ts`). **이 장치를 빼면 화면이 멈춘다** |
| 자동 배포 | `feat/realtime-prototype`에 push하면 곧바로 운영 배포된다 |
| 동시 4개 | 한 프로젝트의 함수는 동시 4개까지. 5번째는 `429` → 클라이언트가 같은 commandId로 재시도한다. **작업자 하나가 여러 요청을 동시에 처리할 수 있으므로 이 4는 런타임 한계가 아니라 라우터의 입장 제한이다** |

### 5-2. 플랫폼 #61 — 동시 실행 4개 한도

- 고칠 곳: `deploy/functions-v2/source/router.mjs:209`(즉시 429 → FIFO 대기열), `src/SupaConsole/src/lib/compose-model.mjs:58`(`--max-parallelism`)
- 릴리스 절차는 #59와 같다: 해시 재고정(`scripts/cli-functions-worker-reuse-pins-20260919.py` 참고) → 이미지 빌드 → 템플릿·전달·정책 파일 교체 → `install` → 일회용 프로젝트로 검증. 플랫폼 인수인계 `docs/cli-implementation/HANDOFF-20260925.md`에 상세가 있다.
- 측정: `scripts/supabase-probe/sweep.mjs`로 동시 1~10. 한 방 안의 명령은 DB 잠금으로 어차피 직렬이라, 효과는 **여러 방이 동시에 돌 때** 나타난다.
- 배경: 작업자(isolate) 하나가 여러 사용자의 요청을 **동시에** 처리한다(운영 관측: 연속 호출에서 작업자 나이가 계속 증가, DB 연결 재사용 2ms). 다만 같은 작업자의 요청들은 `memory_mb`(128MB)를 나눠 쓰므로, 한 요청이 메모리를 많이 쓰면 같은 작업자의 다른 요청도 함께 실패한다. 그래서 무제한이 아니라 대기열 + 적당한 상향이 맞다.
- **확인하지 않은 것**: `--max-parallelism`이 작업자 수를 뜻하는지 동시 요청 수를 뜻하는지. 값을 올리기 전에 edge-runtime v1.74 동작을 확인한다.
- 주의: 릴리스 전에 실행 중인 일회용 프로젝트를 정리한다(템플릿 교체 뒤에는 옛 프로젝트의 관리 명령이 막힌다).
