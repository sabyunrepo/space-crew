# B′ 실측 보고: Edge Function 행 잠금 + 사람별 Broadcast

측정일: 2026-09-19. 대상: 셀프호스팅 플랫폼의 일회용 시험 프로젝트 `crewprobe0919`(`8b616c05-f470-4449-aa25-2287714d0db6`, `https://sb-crewprobe0919.bsh00.com`). 운영 프로젝트 `space-crew-prod`는 조회만 했고 건드리지 않았다.

**쉽게 말하면:** 동시에 명령이 들어와도 게임 상태가 꼬이지 않는다는 것을 실제 서버에서 확인했다. 느려지는 원인은 게임 로직이 아니라 함수 실행 환경(요청마다 새 작업자, 컨테이너 메모리 160MB)이다.

## 구조

```
브라우저 ──POST──▶ Edge Function (요청마다 새 작업자)
                     BEGIN
                     SELECT … FOR UPDATE            ← 방 단위 줄 세우기
                     영수증 확인(command_id)          ← 재전송 중복 방지
                     expect_revision 확인            ← 트릭 넘김 경합 방지
                     UPDATE state, revision+1
                     INSERT 영수증
                     realtime.send(사람별 topic)×N   ← 커밋돼야만 나감
                     COMMIT
각 대원 ◀── private Broadcast `sbp:<프로젝트>:<auth.uid()>` (플랫폼 own-user-v1 규칙)
```

## 결과

측정 위치는 이 맥북이다. 같은 게이트웨이의 가장 가벼운 요청(`/auth/v1/health`) 왕복 p50이 약 280ms라서 절대값은 이 네트워크에 좌우된다. 비교는 이 기준선 대비로 본다.

| 항목 | 결과 |
|---|---|
| 서버 안 처리 (접속, 잠금, 저장, 방송, 커밋) | p50 약 60~80ms. DB 접속이 33~46ms로 가장 큼, 잠금 3.5ms, 커밋과 방송 8ms |
| 함수 호출 전체 왕복 | p50 390~490ms. 기준선보다 약 60~180ms 김 |
| 다른 대원이 방송을 받는 시점 | 요청자가 HTTP 응답을 받는 것과 **거의 동시**(차이 −8~+2ms) |
| 순차 호출(B, E) | 실패 0건, 누락 0건, 순서 뒤바뀜 0건 |
| 동시 폭주 무결성(C, D) | 잃어버린 업데이트 0, 중복 revision 0, 전원 1..N 수신 |
| 멱등 재전송(F, 60개 명령, 동시 4명) | 이중 적용 0건. 결과 불명 뒤 재전송이 `duplicate`로 걸러짐 |
| 트릭 넘김 경합(G, 5명 동시 × 20라운드) | 라운드마다 정확히 1건 적용, 나머지는 `skipped` |

## 시험 중 발견해서 고친 것

| 문제 | 원인 | 조치 |
|---|---|---|
| 모든 호출 502 | Edge Runtime 1.74에 전역 `Buffer`가 없어 postgres.js 로드 실패 | esbuild `banner`로 `node:buffer`, `node:process`, `node:timers` 주입 |
| `permission denied` | `postgres`는 최고관리자가 아니고, 표 주인은 sbp SQL 역할 | 표 권한을 `service_role`에만 부여 (`postgres`가 구성원) |

| sbp 권한 부여 결과 불명 | 운영 API 전송 오류 | 재시도 대신 `has_table_privilege`로 적용 확인, 원장 기록 |

## 한 번 관측된 방송 끊김

F/G만 돌린 6번째 실행에서 5명 전원의 수신이 같은 시각(21:40:35)에 멈췄다. 채널 상태 기록을 추가한 뒤 3회(7, 8번째 실행, 총 수백 건)는 재현되지 않았다. 원인은 **모른다.** 게임에서는 아래 안전장치로 대비한다.

## 실제 게임에 옮길 때의 설계 결론

1. 모든 명령에 `commandId`를 붙이고, 서버는 잠금 **뒤에** 영수증을 확인한다. `503`, `504`, 연결 오류, `429`면 같은 `commandId`로 재전송한다.
2. 트릭 자동 넘김은 `expect_revision`을 조건으로 건다. 지정 1명이 먼저 보내고 나머지는 늦게 보내서 동시 요청 자체를 줄인다(harness의 G2 전략, 아직 실행하지 않음).
3. 화면은 받은 `revision`이 지금보다 클 때만 반영한다. 방송이 끊겼거나 revision 간격이 벌어지면 스냅샷을 다시 조회한다.
4. 준비 버튼처럼 전원이 동시에 누르는 단계가 가장 위험하다(동시 3~5개). 이 단계는 재시도를 전제로 한다.

## 2차: 플랫폼 수정 실측 (2026-09-19 22:00~22:40 KST)

**쉽게 말하면:** 멈춤의 원인은 함수 컨테이너의 메모리 초과 강제 종료(OOM kill)였다. 작업자를 재사용하도록 라우터를 고치자 메모리를 올리지 않아도 멈춤이 사라졌고, 평소 속도도 빨라졌다.

### 원인 확정

- VM(`supabase-d1-01`) 커널 로그: 21:25~21:51 사이 `Memory cgroup out of memory: Killed process (edge-runtime)` 5회. 모두 시험 프로젝트의 함수 컨테이너였다.
- 부하 중 `docker stats`에서 함수 컨테이너가 160MiB/160MiB에 붙었다. 한도는 160MiB에 스왑 160MiB가 더 허용돼 있었다.
- 설정 불일치: 동시 작업자 4개 × 작업자당 최대 128MB가 컨테이너 한도 160MiB보다 크다.

### 적용한 변경 (시험 프로젝트만)

| 변경 | 방법 | 되돌리기 |
|---|---|---|
| 라우터 작업자 재사용 | 플랫폼 브랜치 `sabyunrepo/functions-worker-reuse`의 `router.mjs`를 고정 컴파일러로 빌드한 `main.eszip`(`50572ea5…`)을 `sbp-crewprobe0919` 함수 폴더에만 교체 | 백업 `~/sbp-mainbuild-20260919/backup/main.eszip`(`b6293631…`) 복사 후 함수 컨테이너 재시작 |
| (시험용) 메모리 768MiB | `docker update` | 원래 값 160MiB/스왑 320MiB로 **이미 복구함** |

원본 소스를 같은 절차로 다시 빌드하면 운영 중인 파일과 해시가 같다(`b6293631…`). 따라서 빌드 절차는 재현 가능하다.

라우터 변경 내용: `forceCreate: false`, 작업자 구분 경로에 manifest 해시 추가, 작업자 수명(`workerTimeoutMs`) 60초를 요청 제한시간과 분리, `WorkerAlreadyRetired`이면 새 작업자로 1회만 재시도. 라우터 테스트 10개가 통과했다. 함수 관련 테스트 236개 중 실패 9개는 `main`에서도 같은 목록으로 실패하던 것이다.

시험 함수 변경: 작업자 전역 DB 연결 풀(최대 3), 트랜잭션은 `sql.begin`으로 연결을 고정한다.

### 재사용 상태 정합성 (A~G 전체, 160MiB)

잃어버린 업데이트 0, 이중 적용 0, 트릭 넘김 라운드마다 정확히 1건, 전원 방송 1..N 수신, 결과 불명(503/504/연결 오류) 0건. 429는 5명 동시 시나리오(C)에서만 발생했다(라우터 동시 4개 제한, 예상된 동작). 60초 작업자 수명이 측정 중 여러 번 지났지만 오류는 없었다.

### 남은 일

- 플랫폼 정식 반영: 새 `main.eszip`의 해시 잠금과 artifact-set 라벨, 템플릿·승인 갱신, 관리 서버 릴리스. 지금은 시험 프로젝트 폴더의 파일만 바뀐 상태다.
- 작업자 수명 값 결정: 60초만 시험했다. 5분 같은 더 긴 값은 아직 측정하지 않았다.
- 메모리 한도: 재사용만으로 충분했다. 무거운 함수를 대비해 여유를 줄지는 선택 사항이다.
