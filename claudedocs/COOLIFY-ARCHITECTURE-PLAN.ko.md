# Coolify + 셀프호스팅 Supabase 성능 설계 계획 (Next.js 없이)

작성일: 2026-09-21. 상태: **계획만 있음. 코드는 하나도 바꾸지 않았다.**

**쉽게 말하면:** 지금 Coolify 컨테이너의 Node 서버는 그림 파일만 나눠 주고 놀고 있다. 이 서버에게 게임 심판 일까지 맡긴다. 심판은 Supabase 데이터베이스와 집 안 통로(내부망)로 직접 말한다. 화면 코드(Vite + React)와 데이터는 그대로 둔다.

## 1. 지금 느린 곳 (코드와 기록에서 확인한 것)

| # | 느린 곳 | 근거 | 쉬운 설명 |
|---|---|---|---|
| 1 | 요청마다 사전 확인 요청이 붙을 수 있다 | 화면은 `crew.bsh00.com`, API는 `sb-spacecrew.bsh00.com`. `supabase/functions/_shared/handler.ts`에 `Access-Control-Max-Age`가 없다 | 남의 집에 갈 때마다 "들어가도 돼요?"를 먼저 묻는다. 한 번 묻는 데 약 280ms다 |
| 2 | Edge Function 실행 환경 | `claudedocs/SUPABASE-BPRIME-PROBE.ko.md`: 서버 안 처리 60~80ms, 전체 왕복 390~490ms. 동시 실행 입장 제한, 작업자 메모리 128MB, 수명 300초, 로그 없음 | 요리는 금방인데 주문 줄이 길다 |
| 3 | 4초마다 다시 묻기 | `src/services/supabase.ts`의 `POLL_INTERVAL_MS`. 방송 누락 대비 안전장치다 | 1번과 곱해져 요청이 늘어난다 |
| 4 | 자바스크립트 624KB 한 덩어리 | `dist/assets/index-*.js` 1개. 가이드 페이지와 안 쓰는 연결 방식 코드까지 같이 들어 있을 수 있다 | 책 전체를 받아야 첫 장을 읽는다 |
| 5 | 정적 파일 캐시 표시가 약하다 | `server/app.ts`는 `/cards/`에만 하루짜리 캐시를 준다. 이름에 해시가 붙은 `/assets/*`에는 표시가 없다 | Cloudflare와 브라우저가 "이건 오래 둬도 된다"는 걸 모른다 |
| 6 | 배포 순간 502 | `docs/DEPLOYMENT.ko.md`에 여러 번 기록 | 가게 문을 닫았다 다시 여는 동안 손님이 튕긴다 |

**아직 안 재봐서 모르는 것:** 1번이 실제 요청의 몇 %에 붙는지, 4번에서 안 쓰는 코드가 실제로 얼마나 들어 있는지. 0단계에서 잰다.

## 2. 목표 구조

```
브라우저 ──▶ crew.bsh00.com ── Cloudflare (정적 파일 캐시 + 압축)
               │
               ▼
        Coolify 앱 1개 = 기존 Node 서버 (node:24-alpine, 계속 떠 있는 프로세스)
          ├ 정적 파일   dist/ (Vite 빌드 결과, 지금과 같음)
          ├ /healthz    지금과 같음
          └ /api/crew   ← 새로 추가. 기존 createHandler를 그대로 끼운다
                 ├ 로그인 토큰 서명 검증 (node:crypto, 새 라이브러리 없음)
                 └ postgres.js 연결 묶음 (프로세스에 상주)
                        │  내부망. Cloudflare를 거치지 않는다
                        ▼
                  Supabase Postgres ── select realtime.send(...) ──▶ Realtime
브라우저 ◀── private Broadcast (지금과 같음) ── Supabase Realtime
브라우저 ──▶ Supabase Auth 익명 로그인 (지금과 같음, 브라우저당 처음 한 번)
```

| 맡는 곳 | 하는 일 |
|---|---|
| Coolify의 Node 서버 | 화면 파일, 게임 API, DB 연결 묶음, 로그, 무중단 배포 |
| Supabase | 로그인, 저장, 알림 |
| Cloudflare | 정적 파일 보관과 압축 (서버에 압축 코드를 넣지 않는다) |
| Edge Function `crew-api` | 되돌리기용으로 **그대로 둔다** |

### 왜 작은 변경으로 되는가

- `createHandler`는 웹 표준 `Request → Response` 함수다. Node 24에는 `Request`·`Response`가 기본으로 있다. 변환 코드 수십 줄이면 끼워진다.
- `PostgresRepository`는 `DbPool` 인터페이스에만 의존한다. Deno든 Node든 상관없다.
- 방송은 SQL 안의 `realtime.send()`다. 같은 DB에 붙으면 Node에서도 똑같이 나간다.
- 핸들러가 `?route=` 방식을 이미 받는다. 클라이언트는 기존 빌드 변수 `VITE_CREW_API_URL=/api/crew` 하나로 끝난다. **화면 코드 수정 0줄.**
- 테이블·데이터·게임 규칙은 옮길 것이 없다.

### 하나로 묶는 이유 (화면 서버와 API 서버를 나누지 않는다)

Coolify에서 정적 사이트와 API를 두 앱으로 나눌 수도 있다. 하지만 화면과 API는 같은 계약(`shared/contracts.ts`)으로 묶여 있다. 따로 배포하면 "새 화면 + 옛 API"가 잠깐 섞일 수 있다. 앱 하나면 늘 같이 바뀐다. 정적 파일 부하는 Cloudflare가 대부분 막아 주므로 나눠서 얻는 속도 이득도 없다.

### 기대 효과

| 항목 | 지금 | 목표 (제안값, 0단계 측정 뒤 확정) |
|---|---|---|
| 명령 1번당 요청 수 | 최대 2개 | 1개 (같은 주소라 사전 확인이 없다) |
| 명령 왕복 시간 중간값 | 390~490ms (기준선 280ms) | 기준선 + 40ms 이내 |
| 동시 10개일 때 429·503 | 5번째부터 429 (측정 당시) | 0건 |
| 서버 로그 | 없음 | Coolify 로그 |
| 배포 중 502 | 있음 | 0건 |
| 첫 화면 자바스크립트 | 624KB 한 덩어리 | 게임 시작에 필요한 것만 먼저 |

## 3. 바꾸는 파일 (예상)

| 파일 | 변경 | 크기 |
|---|---|---|
| `server/crew-api.ts` (새 파일) | 연결 묶음, 토큰 검증, `IncomingMessage → Request` 변환 | 약 80줄 |
| `server/app.ts` | `/api/crew` 분기 한 곳, 캐시 헤더 몇 줄 | 작음 |
| `server/index.ts` | DB 모드일 때 `/data` 쓰기 검사 건너뛰기, 종료 시 연결 닫기 | 작음 |
| `server/runtime-package.json` | `postgres` 3.4.9 추가 (버전 고정) | 1줄 |
| `supabase/functions/_shared/handler.ts` | `Access-Control-Max-Age` | 1줄 |
| `src/main.tsx` 또는 `src/App.tsx` | 가이드 페이지를 `React.lazy`로 분리 | 몇 줄 |
| `src/services/index.ts` | 쓰는 연결 방식만 동적 import (측정해서 효과 있을 때만) | 몇 줄 |
| `index.html` | Supabase 주소에 `preconnect` | 1줄 |
| 테스트 | 아래 5절 | 새 파일 2개 |

설계 결정 몇 가지:

- **켜는 스위치는 환경변수 하나.** `CREW_DB_URL`이 있으면 `/api/crew`가 켜지고, 옛 파일 저장 방식의 `/api/*`와 `/ws`는 꺼진다. 이슈 #2(안 쓰는 `/api`·`/ws`가 밖에서 호출 가능한 문제)가 같이 해결된다.
- **프로젝트 UUID는 실행 때 읽는다.** Edge Function은 빌드 때 박아 넣어야 했지만 Node는 환경변수를 자유롭게 읽는다.
- **연결 묶음은 직접 연결 + `prepare: true` + 최대 8개.** 계속 떠 있는 프로세스라 준비된 문장을 재사용할 수 있다. Edge Function에서는 못 쓰던 이득이다. 공유 Postgres라 8개를 넘기지 않는다.
- **jsonb 함정(`$n::text::jsonb`)은 Node에서도 그대로다.** 기존 회귀 테스트를 유지한다.
- **`/healthz`는 가볍게 둔다.** DB 확인을 넣으면 DB가 잠깐 흔들릴 때 화면까지 내려간다. DB 상태는 기존 `/capabilities`의 `backendReady`로 본다.
- **방 만들기·참가 속도 제한은 기존 `IpRateLimiter`를 재사용한다.** `CF-Connecting-IP` 처리가 이미 있다.
- **클라이언트의 재시도, 4초 재조회, 캐시 3초는 그대로 둔다.**

### 보안: 반드시 같이 해야 하는 것

지금 함수는 로그인 토큰을 **읽기만** 한다(`_shared/jwt.ts`). 서명 검증은 플랫폼 관문이 미리 해 준다. Node로 옮기면 관문이 없다. **직접 검증하지 않으면 누구나 남의 자리에 앉을 수 있다.** HS256이므로 `node:crypto`로 서명, 만료 시간, `role=authenticated`, `sub`가 UUID인지를 검사한다. 새 라이브러리는 필요 없다.

## 4. 단계별 계획

### 0단계 — 기준선 측정 + 지금 구조에서 공짜로 얻는 것

1. 측정: `scripts/supabase-probe/sweep.mjs` 동시 1~10, 브라우저 네트워크 기록의 사전 확인 비율, Lighthouse 모바일, 번들 구성 분석.
   → 확인: 결과 표를 이 문서에 붙인다.
2. `handler.ts`에 `Access-Control-Max-Age` 추가. 되돌리기용 경로도 빨라진다.
   → 확인: 연속 명령에서 OPTIONS가 사라진다.
3. 캐시 헤더: `/assets/*`는 1년 immutable, `index.html`은 `no-cache`, `/cards/*`·`/characters/*`는 이름에 해시가 없으므로 하루 유지.
   → 확인: 두 번째 방문에서 `/assets/*`가 네트워크를 타지 않는다.

주의: `feat/realtime-prototype`에 push하면 곧바로 운영에 배포된다.

### 1단계 — 플랫폼 준비 (여기가 막히면 전체가 막힌다)

**2026-09-21 서버에서 읽기 전용으로 확인한 것** (근거: 플랫폼 저장소 `docs/ai/20-kt-cloud-topology.md`, `docs/ai/01-deployment.md`, 그리고 실제 접속)

| 확인한 것 | 결과 |
|---|---|
| 두 서버 위치 | 둘 다 KT Cloud 사설망. Coolify `coolify-d1-01` = `172.25.0.175`, Supabase `supabase-d1-01` = `172.25.0.154` |
| 두 서버 사이 거리 | ping 평균 0.5ms. 아주 가깝다 |
| 접속 방법 | `ssh coolify`로 들어간 뒤 Supabase 서버로 건너간다. Supabase 서버에는 밖에서 바로 못 들어간다 |
| Coolify → Supabase `5432`, `6543`, `8000` | **전부 닫혀 있다.** 열린 것은 SSH(22)뿐이다 |
| Supabase 서버가 듣고 있는 포트 | 프로젝트 API 관문이 `127.0.0.1:18010/18011`(spacecrew), `127.0.0.1:18020/18021`(spacecrew2). 자기 자신만 접근 가능하다 |
| DB 포트 | 도커 내부 네트워크 안에만 있다. 플랫폼 규칙이 "DB 5432와 pooler 6543는 호스트 포트로 게시하지 않는다"이다 |
| 접속 정보를 받는 명령 | `sbp` CLI에 DB 주소나 토큰 비밀키를 내주는 명령이 없다 |

**쉽게 말하면:** 두 서버는 바로 옆방인데 사이에 문이 없다. 그래서 지금은 옆방에 가려고 Cloudflare라는 먼 길을 돌아서 간다. 이 계획의 핵심은 **옆방으로 통하는 문 하나를 내는 것**이고, 그 문은 플랫폼 저장소에서 만들어야 한다.

덧붙여 본 것: Supabase 서버에 `spacecrew`와 `spacecrew2` 두 프로젝트가 떠 있다. 운영 기록(`~/.sbp/crew-queue-20260920/ledger.txt`)에는 "옛 템플릿의 `spacecrew`는 더 관리할 수 없어 다시 만들어야 한다"고 적혀 있고 `spacecrew2`가 그 대체다. 문을 낼 대상 프로젝트를 먼저 정해야 한다. 어느 쪽도 건드리지 않았다.

#### 실험 결과 (2026-09-21, 옛 `spacecrew`에 임시 중계기를 붙여 Coolify 서버에서 측정)

실제 게임 저장 코드(`PostgresRepository`)와 실제 postgres.js를 Coolify 서버의 Node 24 컨테이너에서 돌렸다. 스크립트는 `scripts/supabase-probe/private-path-load.ts`. 끝난 뒤 중계기·방화벽 규칙·접속 정보 파일을 모두 지웠고 포트가 닫힌 것을 확인했다.

| 항목 (서버 안 처리 시간, 중간값) | 준비된 질의 끔 | 준비된 질의 켬 |
|---|---|---|
| DB 한 번 왕복 (`select 1`) | 0.3ms | 0.3ms |
| 새 연결 맺기 (Edge Function이 새 작업자마다 내던 값) | 56ms | 16~56ms |
| 스냅샷 조회 (화면이 4초마다 부르는 것) | 1.0ms | 0.6ms |
| 명령 1건 (잠금, 영수증, 판정, 저장, 방송, 커밋) | 12.1ms | **7.8ms** |
| 5명이 동시에 준비 버튼 (한 방) | 81ms | 55ms |
| 방 8개 × 5명 = 40건 동시 | 101ms (최대 190ms), 거부 0 | 78ms (최대 135ms), 거부 0 |

같은 날 이 맥북에서 잰 공개 주소 왕복(연결 재사용 기준): `crew.bsh00.com` 280ms, Supabase 관문 306ms.

**결론:** 새 구조의 명령 왕복 예상값은 280 + 8~12 = **약 290ms**다. 지금은 390~490ms이고 사전 확인이 붙으면 280ms가 더 든다. 목표(기준선 + 40ms)는 넉넉히 달성된다. KT 클라우드 방화벽은 두 서버 사이의 포트를 막지 않는다(15432 개통 확인). `prepare: true`가 명령 시간을 35% 줄인다.

#### 실험 뒤에 드러난 걸림돌 (플랫폼 쪽, 2026-09-21 확인)

| 걸림돌 | 근거 | 뜻 |
|---|---|---|
| 템플릿을 바꾸는 플랫폼 릴리스는 **그때 있던 프로젝트를 전부 관리 불능으로 만든다** | `src/SupaConsole/src/lib/compose.ts`의 `issueRuntimeGrant`는 프로젝트의 `compose.json`이 **현재 템플릿**으로 다시 그린 것과 글자까지 같아야 통과한다. 백업·정지·삭제가 모두 이 관문을 지난다 | "사설 DB 출입구"도 템플릿 변경이다. 릴리스하면 운영 중인 `spacecrew2`가 관리 불능이 되고, 새 프로젝트를 만들어 운영을 옮겨야 한다 |
| 옛 `spacecrew`는 플랫폼으로 지울 수 없다 | 2026-09-21 `sbp backups create` → `needs_reconciliation`, 작업자 로그 `stage=backup-grant` | 도커 리소스를 손으로 내려도 보관 처리(`archive-empty`)가 같은 이유로 거부되고, 메모리 예약을 쥔 유령 행이 남는다 |
| 새 프로젝트를 만들 자리가 없을 가능성이 높다 | 예약 합계: `spacecrew2` 2656 + `spacecrew` 2656 + 유령 `space-crew-prod` 5376 = 10688MiB. 예산은 16GiB − 4GiB = 12288MiB. 하나 더(2656)면 13344MiB | 릴리스 검증용 일회용 프로젝트도, 운영을 옮길 새 프로젝트도 만들지 못할 수 있다. **실제로 거부되는지는 아직 안 해봐서 모른다** |

그래서 순서가 바뀐다. **"사설 DB 출입구"보다 먼저, 플랫폼에 "관리 불능이 된 프로젝트를 정식으로 정리하는 길"이 있어야 한다.** 그게 없으면 릴리스할 때마다 지울 수 없는 프로젝트가 하나씩 쌓인다.

#### 문을 내는 방법

| 방법 | 내용 | 평가 |
|---|---|---|
| **가. 플랫폼에 "사설 DB 출입구" 기능 추가 (권장)** | 프로젝트의 `db` 포트를 `172.25.0.154:<프로젝트별 포트>`에만 게시한다. `0.0.0.0`은 금지. 방화벽(`DOCKER-USER` 체인)에서 출발지를 `172.25.0.175` 하나로 묶는다 | 가장 빠르다. 다만 템플릿이 바뀌므로 플랫폼 릴리스 절차(해시 재고정 → 이미지 빌드 → 템플릿 교체 → 일회용 프로젝트 검증)를 밟아야 한다. **이 계획에서 가장 큰 일이다** |
| 나. API 관문만 사설 IP로 게시 | Node 서버가 내부망으로 Edge Function을 부른다 | 플랫폼 변경은 가와 비슷하게 드는데 함수의 한계가 남는다. 효과 절반 |
| 다. 플랫폼 밖에서 중계 컨테이너를 따로 띄우기 | Supabase 서버에 작은 TCP 중계기를 손으로 붙인다 | 빠르지만 플랫폼이 모르는 부품이 생긴다. **운영에는 쓰지 않는다.** 일회용 프로젝트에서 "정말 빨라지는지" 재 보는 실험용으로만 쓴다 |

pooler(`6543`) 대신 `db`에 직접 붙는 이유: 계속 떠 있는 Node가 연결 8개만 쓰므로 중간 관리자가 필요 없고, 직접 붙어야 준비된 문장을 재사용할 수 있다.

#### 순서

1. 대상 프로젝트 결정 (`spacecrew` 또는 `spacecrew2`).
2. 실험: 일회용 프로젝트에 방법 다를 잠깐 붙여 Coolify 서버에서 `select 1`과 게임 명령 왕복을 잰다. → 확인: 2절 목표(기준선 + 40ms)가 현실적인지 숫자로 본다. 끝나면 중계기를 지운다.
3. 실험 결과가 좋으면 플랫폼 저장소에 방법 가를 이슈로 올리고 릴리스한다.
4. 전용 DB 역할(예: `crew_api`, `service_role` 구성원, 연결 수 제한 10)을 만든다. `sbp db sql`은 `create role`을 허용하지 않는다. `db migrations`로 되는지는 **아직 안 해봐서 모른다.**
5. DB 비밀번호와 토큰 비밀키를 Coolify 실행 환경변수(비밀값)로 옮긴다. 값은 Supabase 서버의 프로젝트 설정에 있고 CLI로는 못 받는다. 운영자가 서버에서 직접 옮겨야 한다. 문서·채팅·로그에 원문을 남기지 않는다.
   → 확인: Coolify 컨테이너에서 `select 1` 중간값 2ms 안쪽, `has_table_privilege`로 `crew_*` 권한, 위조·만료 토큰이 401.

**아직 안 해봐서 모르는 것:** KT Cloud 쪽 방화벽이 두 서버 사이의 22번 외 포트를 막는지. 지금은 듣는 프로그램이 없어서 구분할 수 없다. 2번 실험에서 같이 드러난다.

### 2단계 — Node 서버에 게임 API 추가

1. `server/crew-api.ts` 작성 → 확인: PGlite로 HTTP 경유 통합 테스트 (방 생성, 참가, 명령, 중복 명령 재전송).
2. 토큰 검증 → 확인: 위조 서명, 만료, 잘못된 role, UUID 아닌 sub 네 가지가 모두 401.
3. `CREW_DB_URL` 스위치와 옛 `/api`·`/ws` 끄기 → 확인: `playwright.server.config.ts`(서버 모드 회귀)가 스위치 없이 그대로 통과.
4. 종료 처리: SIGTERM에서 새 요청을 막고, 처리 중인 요청을 기다린 뒤 연결을 닫는다 → 확인: 부하 중 재시작에도 결과 불명 명령이 재전송으로 한 번만 적용된다.

### 3단계 — 화면 묶음 줄이기

1. 가이드 페이지 `React.lazy` 분리.
2. 번들 분석에서 안 쓰는 연결 방식(mock, server) 코드가 실제로 보이면 동적 import로 분리. 안 보이면 하지 않는다.
3. `index.html`에 Supabase 주소 `preconnect` (로그인과 알림 연결을 미리 연다).
   → 확인: 첫 화면에 받는 자바스크립트 크기 전후 비교, 기존 Playwright UI 테스트 통과.

### 4단계 — Coolify 설정

| Coolify 기능 | 어떻게 쓰나 | 효과 |
|---|---|---|
| Dockerfile 빌드 (기존 유지) | 빌드 변수에 `VITE_CREW_API_URL=/api/crew` 추가 | 화면이 같은 주소의 API를 부른다 |
| 실행 환경변수 (비밀값) | `CREW_DB_URL`, `CREW_JWT_SECRET`, `CREW_PROJECT_ID`, `CREW_ALLOWED_ORIGINS` | 비밀값이 브라우저 묶음과 이미지에 안 들어간다 |
| 헬스 체크 + 무중단 교체 | `/healthz` 기존 사용. 502가 왜 나는지는 Coolify 설정(고정 포트, 컨테이너 이름, 볼륨)을 봐야 안다. **아직 안 봐서 모른다** | 배포 중 502 제거 |
| 네트워크 | Supabase와 같은 도커 호스트면 같은 네트워크에 연결, 아니면 내부 IP | DB까지 가장 짧은 길 |
| 자원 제한 | 메모리·CPU 상한 | 다른 서비스 보호 |
| 배포 브랜치 분리 | 운영은 `main`, 작업 브랜치는 시험 주소 | "push하면 곧바로 운영"이라는 지금의 위험 제거 |
| `/data` 볼륨 | 안정된 뒤 제거 (그 전에는 되돌리기용으로 유지) | 무중단 교체가 단순해진다 |

오래된 데이터 정리는 기존 방식(서버가 뜰 때 30일 지난 방 정리)을 DB에도 똑같이 적용한다. `crew_rooms`를 지우면 나머지 표는 `on delete cascade`로 같이 지워진다. 별도 예약 작업은 만들지 않는다.

Cloudflare: `/api/*`는 캐시 제외. 나머지는 3단계의 캐시 헤더를 따른다.

### 5단계 — 전환과 되돌리기

1. 시험 주소(예: `crew-next.bsh00.com`)에 같은 이미지를 올리고 일회용 sbp 프로젝트 DB에 붙인다.
2. `E2E_BASE_URL=<시험 주소>`로 다인 E2E 19개 + Aside 실제 조작 (기존 배포 정책 그대로).
3. `sweep.mjs` 재측정 → 2절 목표와 비교.
4. 운영 앱의 환경변수를 바꿔 전환한다.

되돌리기는 두 겹이다. (가) `VITE_CREW_API_URL`을 비워 재배포하면 화면이 다시 Edge Function을 부른다. (나) Coolify에서 직전 커밋 SHA 배포. 같은 DB를 쓰므로 데이터는 손댈 것이 없고, 전환 중에 진행하던 방도 이어진다.

### 6단계 — 측정한 뒤에만 하는 것

| 후보 | 하는 조건 | 내용 |
|---|---|---|
| 알림을 Node의 WebSocket으로 직접 보내기 | 전환 뒤에도 방송 누락이 계속 관측될 때 | 서버에 `ws`가 이미 있다. 배포 중 두 대가 잠깐 같이 뜨므로 `LISTEN/NOTIFY`로 서로 알려야 한다. 일이 커서 근거 없이는 하지 않는다 |
| 가벼운 재조회 | 4초 재조회가 DB 부하로 보일 때 | "내 revision 이후 바뀐 게 있나"만 묻고 없으면 빈 응답 |
| 카드 이미지 크기별 제공 | 모바일 첫 게임 화면이 그림 때문에 느릴 때 | 카드 41장이 합계 4MB다. 작은 화면용을 따로 만든다 |

**넣지 않는 것:** Next.js, Redis, 서버 여러 대, 화면·API 앱 분리, 서버 쪽 압축 코드.

### 7단계 — 정리

- `docs/DEPLOYMENT.ko.md`, `docs/FRONTEND-HANDOFF.ko.md`, `docs/API.ko.md`, `.env.example` 갱신.
- 이슈 #2 닫기. 옛 서버 모드 코드와 `/data` 볼륨을 완전히 뺄지는 안정된 뒤 사용자가 결정한다.
- Edge Function은 한동안 되돌리기용으로 유지한다.
